## Product and architecture

SessionIQ is a local-first music-project notebook and analysis assistant, not a DAW or music generator.

- Python/FastAPI backend: `src/sessioniq/`.
- Audio analysis: librosa with a WAV fallback; MIDI: pretty_midi/mido; text notes produce action items.
- React 19 + TypeScript + Vite + Tailwind frontend: `web/`.
- Retrieval: lexical metadata search plus optional local ChromaDB.
- Answer engine: optional OpenAI-compatible endpoint/Ollama, otherwise deterministic rules.
- Current persistence: Python in-memory state plus JSON index and files under `.sessioniq-data`.
- Typical API port: 8000; typical frontend port: 5173.
- `.env` is private and ignored. Do not expose its contents or include it in a commit.
- Runtime libraries, uploads, logs, build artifacts, node_modules and the Python venv are ignored.

## Original findings and what changed

### 1. Project-folder collisions and deletion safety

Original bug: names such as `Song A`, `Song-A`, and `SONG A` normalize to the same folder slug. Deleting a project previously used recursive directory deletion, which could erase another project's files.

Implemented:

- `project_slug()` remains a human-readable hierarchy helper.
- `safe_upload_path()` appends a 16-character SHA-256 suffix derived from the normalized, case-sensitive project name to the project path. This separates new uploads whose display names otherwise slug identically.
- This is **not a new permanent project-ID database**. Project identity in the domain model is still mostly the name/path. Be precise about that distinction.
- Existing stored paths continue to work. No mass migration was run against the user's files.
- Deletion now selects owned asset files, checks containment within `UPLOAD_ROOT`, and moves them into `UPLOAD_ROOT.parent / "trash" / <uuid>`.
- It does not recursively delete a project directory.
- Shared physical files referenced by non-deleted assets are preserved.
- Recovery manifests include original paths, asset metadata, and task statuses.
- Trash is outside the publicly served `/uploads` directory.
- Trash retention is indefinite; there is no restore/purge UI yet.
- Path handling rejects invalid upload basenames and checks containment; moves also check the source path.

Important functions: `safe_upload_path`, `move_stored_file` in `project_workspace.py`; `_trash_assets`, `_move_asset` in `api.py`.

### 2. Atomic persistence and mutation rollback

New `src/sessioniq/persistence.py`:

- Writes a unique temporary file next to the destination.
- Flushes and fsyncs before `os.replace`.
- Retains the previous readable index as `library-index.json.bak`.
- Rejects NaN/Infinity in serialized JSON.

`api.py` now has:

- `STATE_LOCK`, an `RLock`.
- `@mutation` on mutation endpoints and upload commit.
- Deep-copy snapshots of in-memory assets, task statuses, ordering and preferences.
- A file-move journal used to restore files if a mutation/save raises.
- On failure, the retriever's in-memory assets are reset and optional vectors are disabled until restart, avoiding stale vector results after a partial mutation.
- `@synchronized` on selected readers, including library/memory/search; chat copies retrieved sources, preferences and tasks under the lock before calling the model.
- Corrupt/unreadable index JSON causes an explicit startup failure with backup guidance rather than silently starting an empty library.
- Metadata for missing files is retained with a warning rather than discarded.

Limitations: these are **single-process** protections. The filesystem and index are not a crash-atomic database transaction. A killed process during a move can require manual recovery. The backup is one index save behind, not a complete snapshot of all files. These caveats are documented in README.

### 3. Task IDs and completion

Original bug reproduced: mark a task Done, rename its project, then the task becomes To do because its ID includes the project name.

Implemented:

- New task ID is derived from stable asset ID + task description, independent of project/file name.
- Legacy overrides keyed by project/name/description are copied to new IDs on load/summarization, before rename/move.
- Migration is persisted on the next successful save; startup itself does not rewrite the real index.
- Repeated identical action descriptions within one asset are deduplicated.
- `ProjectTask` now includes optional `asset_id`.
- Changing the actual description still changes its derived ID. Full editable task entities are not implemented.

### 4. Health and progress semantics

Original problems: artwork was tagged Reference and therefore counted as a reference *track*; a file named final could satisfy the master check regardless of type; All Projects showed the first project's health; zero-task projects displayed 0% progress.

Implemented:

- Reference/master checks require audio assets with explicit Reference/Ready status.
- Existing filename-based ingestion status inference remains; this is not a complete release-readiness model.
- Cards display “x of y tasks done” or “No tasks yet” instead of ambiguous percentages.
- The exact selected project's checklist is expandable and labeled readiness.
- All Projects and album-level scope no longer show an arbitrary child's health score.
- No new aggregate album/library readiness score was invented.

### 5. Assistant preferences, saved tasks and validation

Implemented:

- `GroundedAssistant` accepts `preferences` and `tasks`.
- Chat passes saved preferences and current task status records.
- Optional LLM receives producer preferences and relevant task records, with instructions that source/preference text is data and current task status is authoritative over stale TODO text.
- Rules-based task answers and summaries use saved task statuses when supplied.
- Offline rules do not personalize their wording from preferences; README says so.
- Citations now have optional `asset_id`. Deterministic citations populate it and LLM instructions request it.
- Validation rejects ambiguous citations when an existing filename matches multiple assets without sufficient identification.
- Numeric checks recognize limited explicit BPM, peak_db, rms_db, duration and note_count patterns, accepting appropriate displayed rounding.
- A made-up 999 BPM citation/claim against a 120 BPM asset is now rejected.
- LLM validation uses only the sources actually included in its capped prompt.
- Model client has 30-second timeout and zero retries, followed by existing rules fallback.
- Prompt version: `v1.3.0`.
- Quality reporting no longer labels mere citation success “low hallucination risk”; successful automated checks report risk as `not assessed` and show limitations.

This is **not complete factual verification**. Arbitrary natural-language claims, source text meaning, and every possible numeric format are not checked. Do not restore the earlier overconfident quality messaging.

### 6. Upload behavior

Implemented:

- Each request gets its own staging directory.
- File types are checked before ingestion.
- Uploaded content is read in 1 MiB chunks, with a 512 MiB per-file cap.
- Synchronous analysis is dispatched with FastAPI's `run_in_threadpool` rather than executed directly on the async event loop.
- The batch enters the library only when every file has analyzed successfully.
- Commit runs through the mutation/rollback mechanism.
- Failed staging data is cleaned up.
- UI enters its uploading state before reading client-side metadata.

This is **not a durable background job queue**. The HTTP upload still waits for analysis and there is no persisted per-file progress, cancellation/retry, restart recovery, or concurrency/resource budget.

## Remaining work and review priorities

### Before committing or expanding the change

Do a focused diff review rather than another broad project assessment. Tests pass, but the implementation has not had an independent reviewer. In particular:

1. **Rollback failure handling — addressed in continuation:** filesystem restore errors are logged and attached to the original exception; remaining restores are attempted, and in-memory/retriever state is restored in a finally block. A regression reproduced the old failure and now passes. Files that cannot be restored still require manual recovery; this is not a durable recovery system. See `docs/UPDATE-LOG.md`.
2. **Global move journal — nesting guarded in continuation step 2:** `@mutation` now rejects re-entry before snapshotting, clearing the journal, running the inner body, or saving. An active flag is protected by the existing `STATE_LOCK` and resets in `finally`. Uncaught nesting errors trigger the outer rollback. Synchronized reads still work inside mutations. Two regression cases cover file moves and metadata-only changes, unchanged committed index, restored file/state, and a successful subsequent mutation. The global journal remains single-process; a request-local transaction design is deferred. Use undecorated helpers inside a mutation, not another decorated mutation.
3. **Crash consistency:** atomic JSON plus in-process rollback does not cover process termination mid-move. A durable journal/SQLite migration would need an explicit design and migration/recovery tests.
4. **Performance at scale:** mutation snapshots copy the library; requests still serialize metadata for all files; some API/UI paths iterate the entire catalog. No thousands-of-assets benchmark was run.
5. **Numeric validation limits:** regex checks are intentionally partial and answer-level matching pools cited values. A value from the wrong cited file can still slip through some phrasings; arbitrary note quotations containing numbers may need careful treatment. Keep the limitation wording.
6. **Player timing — partial follow-up in step 3:** explicit slider seeks now immediately update displayed time and save resume position; previously they relied on throttled `timeupdate` or later pause/end events. Manual acceptance remains open: seek twice within two seconds while paused, refresh, verify the second position, then check seeking during playback. Browser automation in this continuation changed the range input DOM value without seeking the media, so it did not verify the fix. Cached-media event ordering, selection changes during load, and broader refresh/resume behavior remain open. Earlier browser checks establish persistent playback across views, not exhaustive media reliability.
7. **Unsaved note behavior:** inspect external library refreshes and queued saves while editing/switching assets; browser-local drafts are useful but are not a synchronized notes database.
8. **Frontend maintainability:** App still contains many components and some long JSX lines. Secondary API handling and explicit types could be improved incrementally. Avoid a broad cosmetic reformat that hides functional changes.
9. **Docs/dependencies:** old screenshots and some broad README feature descriptions predate this update; unused WaveSurfer/other dependencies may remain. Do not claim all original README functionality was revalidated.

These are review targets and known limitations, not claims that new failures were reproduced.
